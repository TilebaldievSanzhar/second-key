# ADR 0001 — Отдельный репозиторий, монорепо backend + frontend

Статус: принято · 15.10.2026

## Контекст

Ядро проверки документов живёт в `procdesk` — стенде под челлендж MOST BI × BI Group
(Казахстан, закупочный стол снабженца, бенчмарки v1–v11, скрейперы goszakup, исследовательские
скрипты). Новый продукт «Второй ключ» — другой покупатель (собственник), другая юрисдикция (КР),
другой контур (аудит и контроль цен по выгрузкам 1С). Нужна чистая история и продовый каркас.

## Решение

1. `second-key/` — отдельный git-репозиторий в корне `development_challenge`; внешний репозиторий
   его игнорирует.
2. Монорепо: `backend/` и `frontend/` в одном репозитории, один `compose.yaml`.
3. Движок аудита **переносится** из procdesk (`secondkey.engine`), а не подключается как зависимость.
   procdesk замораживается как стенд казахстанского трека.

## Почему

- Монорепо: изменения API и интерфейса уходят одним коммитом; типы фронта генерируются из
  OpenAPI бэкенда; один CI и одна команда запуска. Для команды из 1–5 человек отдельные репозитории
  дают только трение.
- Перенос, а не зависимость: у procdesk исследовательский код и данные, которые не нужны в проде;
  общий пакет пришлось бы версионировать между двумя продуктами с разной скоростью.

## Последствия

- Исправления движка делаются здесь; в procdesk переносятся только при необходимости трека BI Group.
- Тесты движка переехали вместе с кодом и являются регрессией переноса.
