# ADR 0006 — Связки снабженца и поставщика

Статус: принято · 16.10.2026 · исследование — [SUPPLIER_LINKS.md](../product/SUPPLIER_LINKS.md)

## Решение

Модуль `backend/src/secondkey/engine/links.py` после правил цены ищет следы связки в трёх группах и
поднимает вопрос (находка `LINK`), когда у пары «снабженец — поставщик» сошлись следы из двух групп
или ИНН поставщика совпал с ИНН сотрудника.

| Группа | Следы |
|---|---|
| цена | L-01 премия пары к закупкам других снабженцев той же позиции в те же недели; P-01/P-02/P-03 по строкам пары от 50 тыс. сом |
| поведение | L-04 почти весь оборот через одного снабженца; L-05 появился вместе с новым снабженцем; L-06 новый поставщик забрал позицию и он дороже |
| личность | L-09 входящие номера подряд; L-10 юрлицо моложе года или ИП моложе 23 / старше 70 — по номеру ИНН; L-11 общие телефон, счёт, e-mail; L-12 ИНН = ИНН сотрудника |

Пороги — в `AuditConfig` (`link_*`). Досье всех поставщиков со всеми следами, в том числе не ставшими
вопросом, — в таблице `run_suppliers`, API `GET /api/audits/{id}/suppliers` (собственник и финансы).

## Принципы

- **Один след — не вопрос.** Почти любой след объясним (молодая фирма, узкий поставщик, закреплённые за
  снабженцами категории); совпадение независимых — повод спросить. Исключение — поставщик = сотрудник.
- **Связка денег не добавляет.** У находки `LINK` вклад строк — 0; её `overpayment` — справочно (крупнейший
  ценовой след по строкам пары). Итог прогона, разбивка по правилам и «подтверждено» считаются без `LINK`.
  В интерфейсе связка — сигнал.
- **Снабженец видит вопрос о покупках, а не досье на себя.** Текст находки — только факты о покупках и ценах;
  следы поведения и личности — в `evidence`, их отдаёт API только собственнику и финансам.
- **Сравнение — только там, где есть с кем.** Премия пары и эксклюзивность считаются по позициям, которые
  покупают ≥ 2 снабженца: закреплённые категории — норма, а не сигнал.
- **ИНН сотрудников не покидают 1С.** Обработка шлёт SHA-256 от «соль:ИНН»; соль организации выдаёт
  `GET /api/integrations/ping`, сервис хэширует ИНН поставщиков так же. Это псевдонимизация, а не
  анонимизация: соль у организации и у сервиса. Флажок «Сверять с сотрудниками» в обработке — решение клиента.
- **Дата в ИНН — «по номеру».** Структура ИНН юрлиц (дата регистрации) установлена по выборке, не по
  официальному описанию — в текстах «по номеру ИНН», сверка с реестром — когда появится доступ (шаг 1.22).

## Данные

Контракт выгрузки (`integrations/contract.py`): в строке — `doc_in_no`, `doc_in_date` (входящие номер и дата);
рядом со строками — `suppliers` (реквизиты из карточек контрагентов) и `staff` (имя, хэш ИНН, должность).
Таблица Excel — колонки «Вх. номер», «Дата вх.», «Телефон/Адрес/Расчетный счет контрагента». OData — те же
поля как необязательные: если их нет в публикации, выгрузка идёт без них.

## Качество

`secondkey bench` — подсаженные связки в синтетике (5 пар: «свой» ИП, новый снабженец с молодой фирмой,
два «конкурента» с одним телефоном и счётом, ИП-прораб) и метрики `links`: доля найденных пар, доля
ожидаемых следов, связки сверх подсаженных. CI падает, если найдены не все пары (`--min-links 1.0`).

## Интерфейс и отчёт (неделя 2)

- `GET /api/audits/{id}/links` — матрица «снабженцы × поставщики», связки со следами; `GET /api/audits/{id}/suppliers/{sid}` —
  досье с ценами по позициям против других поставщиков и госзакупок в те же месяцы (± 15 дней). Оба — собственник и финансы.
- `GET /api/findings/{id}/alternatives` — «где дешевле» по трём главным позициям вопроса: медиана цен ваших поставщиков
  за последние 90 дней проверки (давно не покупали — последние три цены с датой) и медиана госзакупок; видит каждый,
  кому виден вопрос, в том числе снабженец — это факты о ценах, а не о людях.
- У связки свои подписи решений: «Связка подтверждена / Обосновано / Ошибка учёта»; статусы те же, деньги «подтверждено»
  считаются без LINK.
- Отчёт для печати — в двух вариантах: полный (`report.html`) для собственника и финансов, без следов поведения и
  личности поставщика (`report-basic.html`) — для бухгалтера и наблюдателя. Старые прогоны без второго варианта и со
  связками бухгалтеру не отдаются (403).
- Текст для WhatsApp: строка о связках, ждущих пояснения; в «топ сумм» связки не попадают (сумма повторяет ценовые
  вопросы). Модуль `owner_digest` — версия 1.1.

## Оплаты, реестр, сеть (неделя 3)

- **Оплаты** (`engine/payments.py`): по поставщику события во времени — поставка гасит ранние оплаты (предоплата),
  оплата гасит ранние поставки (постоплата с задержкой). Аванс без поставки — превышение оплат над поставками не
  ниже 100 тыс. сом, которое держится 30+ дней: вопрос **P-09** (вклад 0 — деньги под риском, не переплата;
  доказательство — оплаты и поставки с даты, когда превышение возникло). След **L-07** (поведение): аванс; ≥ 80%
  поставок по предоплате, когда остальным заранее платят ≤ 30%; оплата за 1–3 дня, когда остальным — через 14+.
- **Реестр** (`engine/registry.py`, `registries/`, `services/registry.py`): своя ручная проверка организации важнее
  свежей записи агрегатора; записи агрегатора — публичные сведения, общий кэш (org_id пусто) на 30 дней;
  ручные — только своей организации. Следы: L-13 (недействующий, банкрот, недобросовестный — НДС к зачёту под
  риском до 12/112 оборота), общий руководитель или учредитель (фамилия и инициалы) в L-11, дата регистрации по
  реестру в L-10. Агрегатор вызывается задачей `registry.fetch_run` по кнопке в «Связях».
- **Пересчёт связок** (`services/links_refresh.py`): после новых сведений реестра следы и вопросы LINK проверки
  пересчитываются из БД без нового прогона; у существующей пары меняются текст и следы, статус, ответ и решение
  остаются; пара, переставшая сходиться, удаляется, только если на неё ещё не ответили.
- **Сеть** (`services/network.py`): только организации с согласием, ≥ 3 других компаний и ≥ 10 покупок по паре
  «ИНН × позиция», среднее из медиан по компаниям с округлением до 10 сом, покупки за последний год каждой
  проверки. След L-03 «двойная цена» — в группе «цена», деньги справочно.
