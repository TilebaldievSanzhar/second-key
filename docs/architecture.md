# Архитектура

## Контекст

```
 Собственник ─┐                    ┌──────────────── docker compose ────────────────────────────┐
 Бухгалтер ───┼── браузер ──► web (nginx: статика SPA, /api → api)                              │
 Снабженец ───┘                    │        │                                                    │
                                   │        ▼                                                    │
                                   │      api (FastAPI) ──► postgres (данные, деньги, находки)   │
                                   │        │   ▲   └─────► s3 (RustFS: выгрузки, отчёты)         │
                                   │        │   │ SSE                                             │
                                   │        ▼   │                                                 │
                                   │      redis (очередь taskiq, pub/sub прогресса)               │
                                   │        ▲                                                     │
                                   │   worker (taskiq) ── движок аудита ── postgres, s3           │
                                   │   scheduler (taskiq) ── курсы НБКР, цены госзакупок КР       │
                                   └─────────────────────────────────────────────────────────────┘
```

## Поток аудита

1. `POST /api/uploads` — файл уходит в S3, API читает шапку и возвращает найденные колонки
   и первые строки (пользователь подтверждает сопоставление).
2. `POST /api/audits` — создаётся прогон `queued`, коммит, затем задача `audit.run` ставится в очередь
   (Redis Streams, consumer group: задача подтверждается после выполнения и не теряется при падении воркера).
3. Воркер: импорт → нормализация → правила → запись строк и находок → HTML-отчёт в S3.
   Каждая стадия обновляет `status/progress` в БД и публикует событие в `run:{id}`.
4. Интерфейс слушает `GET /api/audits/{id}/events` (SSE: первое событие — состояние из БД, дальше —
   смена стадий до `done`/`failed`) и затем читает сводку, находки, историю цен позиций.
5. Два ключа: снабжение отвечает (`POST /api/findings/{id}/answer`), собственник решает
   (`POST /api/findings/{id}/decision`: confirmed | justified | data_error), решение отменяется
   (`POST /api/findings/{id}/reopen`) — вместо диалогов «вы уверены?».

Полный список эндпоинтов — `http://localhost:8000/api/docs` (в dev) или `secondkey openapi`.

## Слои бэкенда

| Пакет | Ответственность | Зависит от |
|---|---|---|
| `secondkey.engine` | чистая предметная логика: импорт таблиц, нормализация, правила, отчёт | ничего (без IO и настроек) |
| `secondkey.refdata`, `secondkey.market` | курсы НБКР, НДС, сбор цен госзакупок КР | httpx |
| `secondkey.db` | модели SQLAlchemy, сессии | SQLAlchemy |
| `secondkey.services` | сценарии: аудит, рынок и курсы, организации, хранилище, безопасность, прогресс | engine, db |
| `secondkey.api` | HTTP: схемы, роутеры, зависимости, SSE | services |
| `secondkey.worker` | брокер, задачи, расписание | services |

Правило зависимостей: `engine` ничего не знает о БД и HTTP — его тесты и бенчмарки работают
на чистых данных, как в procdesk.

## Данные

- `organizations(settings)`, `users`, `memberships(role, alias)` — арендатор, пороги правил и роли: owner, finance,
  accountant, buyer, viewer; `alias` — как сотрудник записан в 1С («Асанов Б.»).
- `uploads` — файл в S3 (ключ, sha256, размер) и предпросмотр: найденная шапка, сопоставление колонок, первые строки.
- `audit_runs` — прогон: статус, прогресс, параметры правил, итоги (оборот, переплата, период).
- `purchase_lines` — строки учёта + результат нормализации (позиция, базовая единица, цена) + итог переплаты строки.
- `findings` + `finding_lines` — находки с деньгами по строкам; статус работы с находкой
  (`open → answered → confirmed | justified | data_error`), ответ снабжения, решение собственника.
- `market_points` — рыночные цены по позициям (госзакупки КР, позже — обезличенные данные клиентов);
  уникальность по (источник, номер закупки, позиция, дата, цена) — повторный сбор не плодит дубли.
- `fx_rates` — курсы НБКР по датам (задача по расписанию).

## Безопасность

- JWT в httpOnly-cookie (`SameSite=Lax`, `Secure` в проде), пароли argon2id.
- Все запросы к данным фильтруются по `org_id` текущего членства; роль проверяется на уровне роутера.
- Снабженец (buyer) видит только находки, где ответственный = его `alias`; сводка, все строки и отчёт
  компании ему недоступны (403) — продукт не превращается в инструмент доносов внутри отдела.
- Файлы клиентов — только в S3 по ключам с префиксом организации; наружу — через API.
- Документы — данные, не инструкции: при подключении LLM действуют сенсоры инъекций из procdesk.

## Очереди и фоновые задачи

| Задача | Когда | Повторы |
|---|---|---|
| `audit.run` | по запросу `POST /api/audits` | нет: ошибка видна пользователю, `POST /api/audits/{id}/retry` |
| `refdata.fetch_fx` | ежедневно 10:30 Asia/Bishkek | 3 раза с растущей паузой (SmartRetryMiddleware) |
| `market.collect_kg` | воскресенье 03:00 Asia/Bishkek | 3 раза, кэш ответов портала на томе `marketcache` |

Тяжёлые стадии движка выполняются в отдельном потоке (`asyncio.to_thread`), event loop воркера свободен.
Прогон идемпотентен: повтор пересобирает строки и находки прогона с нуля.

## Окружения

| | dev (`docker compose up`) | prod (`-f compose.yaml -f compose.prod.yaml`) |
|---|---|---|
| Образ бэкенда | `dev`: editable, dev-зависимости, hot reload (polling для Docker Desktop) | `runtime`: только `uv.lock --no-dev`, non-root uid 10001 |
| Фронт | Vite dev server :5173, `/api` → api | nginx :8080: статика + `/api`, CSP, SSE без буферизации |
| Логи | читаемые | JSON, `request_id` из nginx |
| Swagger | `/api/docs` | выключен |
| Порты наружу | db, redis, s3, api, web — только 127.0.0.1 | только web |

Хранилище файлов — S3 API. Локально RustFS (Apache-2.0): образы MinIO с Docker Hub с 2026 года
недоступны. В проде — любой S3 (`SK_S3_ENDPOINT_URL`), код не меняется.
